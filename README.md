## Открыть текущую версию

При запущенном приложении: [панель](http://127.0.0.1:8000/) и [админка](http://127.0.0.1:8000/admin/).

Для локального просмотра создан `local-owner`. Пароль находится в [локальном файле доступа](<C:/Users/Vladislavv/Documents/ChatGPT/AI-дайджесты бот/var/local-admin.txt>); файл исключён из Git и Docker. Эта учётная запись используется только для разработки. Повторная команда создания не меняет пароль.

На текущем компьютере окружение уже установлено, миграции применены, каталог импортирован. После остановки сервера его можно запустить из корня проекта:

```powershell
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000 --noreload
```

Локальная база — `var/dev.sqlite3`. Она сохраняется между запусками и исключена из Git. SQLite применяется для проверки админки; серверная база остаётся PostgreSQL. Локальный сервер слушает только этот компьютер. После изменения Python-кода с `--noreload` его нужно перезапустить.

## Установка на другом компьютере

Требуется Python 3.12 или 3.13. Серверная конфигурация рассчитана на 3.13; текущая локальная проверка выполнена на 3.12.14.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py import_seed
.\.venv\Scripts\python.exe manage.py create_local_admin
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000 --noreload
```

Если команда `python` не установлена в PATH, укажите полный путь к интерпретатору. На Linux вместо `.venv\Scripts\python.exe` используется `.venv/bin/python`. `requirements.lock` фиксирует установленные версии библиотек; проверка всей сборки на Linux/3.13 ещё предстоит.

- Проверить предложения по объединению похожих публикаций и при необходимости исправить результат автоматической группировки.
- Посмотреть журнал AI-запросов, настроить месячный предел и собрать полный RU/EN-предпросмотр с одинаковым порядком событий и ссылками.
- Посмотреть поколения подписчиков, неизменяемую историю настроек, зафиксированный состав отправок, части и результаты попыток.

Данные импортируются неактивными. В админке источник можно добавить, сразу связать с одной или несколькими подборками и включить действием «Включить выбранные источники без технической проверки». Действие само задаёт штатный адаптер. Для сайта в поле RSS указывается адрес RSS/Atom-ленты; если поле пустое, система попробует использовать основной адрес источника как ленту. Действие «Исключить выбранные источники из сбора» немедленно убирает источник из будущих циклов без удаления истории. YouTube нельзя активировать в первой версии. Сбор одного источника для диагностики запускается явно:

```powershell
.\.venv\Scripts\python.exe manage.py collect_source source_id --limit 10
```

Для Telethon задаются `TELEGRAM_SOURCE_API_ID`, `TELEGRAM_SOURCE_API_HASH`,
`TELEGRAM_SOURCE_PHONE` и путь `TELEGRAM_SOURCE_SESSION_PATH`. Первый вход выполняется
интерактивно из защищённого терминала — команда запросит код Telegram и, если включён, пароль
двухэтапной проверки:

```powershell
.\.venv\Scripts\python.exe manage.py init_telethon_session
```

Необязательная диагностика доступа к каналам пилота не сохраняет тексты публикаций:

```powershell
.\.venv\Scripts\python.exe manage.py probe_telegram_sources --wave A --output research\live_telegram_probe_wave_a.json
```

После включения планировщик автоматически начинает собирать источник. Повторные проходы получают новые посты после сохранённого
`message_id` и повторно проверяют небольшой хвост уже известных сообщений для обнаружения правок.
При ответе Telegram `FloodWait` фоновое задание переносится не раньше указанного платформой срока;
ожидание ограничивается семью днями, после чего остаётся видимая повторяемая ошибка для оператора.

Сборщик сайтов принимает только публичные HTTP(S)-адреса, перепроверяет каждый редирект и DNS-ответ, ограничивает тип и размер ответа, поддерживает ETag/Last-Modified и сохраняет фрагмент RSS при неудачном извлечении статьи. Публичные Telegram-каналы собираются отдельным Telethon-аккаунтом только по административному allowlist; личные чаты, поиск и скачивание медиа не поддерживаются. Решение и принятый риск описаны в [политике Telegram-источников](<C:/Users/Vladislavv/Documents/ChatGPT/AI-дайджесты бот/docs/TELEGRAM_SOURCE_POLICY.md>). Полные исходные тексты очищаются через `purge_expired_source_text`; срок по умолчанию — 90 дней, неизменившееся повторное получение его не продлевает.

Первый AI-адаптер использует OpenRouter Chat Completions со строгой JSON Schema:
`openai/gpt-5.4` для русского черновика и `openai/gpt-5-mini` для английского перевода. Ключ
задаётся в `OPENROUTER_API_KEY`, а месячный предел — в разделе «Бюджеты AI по месяцам».
Запрос требует поддержку всех параметров, запрещает сбор данных провайдером и включает ZDR.
Начальный лимит `$0`, поэтому без явной настройки платный запрос блокируется до обращения к API.

После появления публикаций и события технический RU/EN-прогон выполняется так:

```powershell
.\.venv\Scripts\python.exe manage.py suggest_event_groups --hours 48
.\.venv\Scripts\python.exe manage.py generate_event_cards event_id slot_key
.\.venv\Scripts\python.exe manage.py build_edition_preview collection_id schedule_id --main ru_card_id[,ru_card_id] --additional ru_card_id[,ru_card_id]
```

Сформированный Telegram HTML делится между историями с запасом до ограничения сообщения. Английский выпуск строится только из переводов точных RU-редакций и сохраняет состав, порядок и ссылки.

Штатный редакционный конвейер не требует ручных действий. Перед каждым слотом он группирует публикации, создаёт одиночные события, назначает их в подборки по источникам и ключевым словам, ранжирует, создаёт RU-карточки и естественные EN-переводы, собирает выпуск и публикует связанную языковую пару. Админка сохраняет просмотр и корректировку событий, маршрутов и отбора как инструмент управления и расследования ошибок.

Слой подписок поддерживает отдельные состояния регистрации, активности, доступа, достижимости чата, диалога и удаления данных. Сохранение языка, подборок и частоты создаёт новую неизменяемую редакцию. Пауза сохраняет выбор и отменяет ещё не переданные автоматические части. Повторный `/start` возобновляет завершённую приостановленную подписку без досылки истории.

Подготовка отправки не вызывает Telegram и доступна отдельной командой:

```powershell
.\.venv\Scripts\python.exe manage.py prepare_delivery subscriber_uuid 2026-09-12T13:00:00+03:00
```

Команда принимает только опубликованные выпуски одной редакции расписания и периода, фиксирует манифест, удаляет повторы событий между подборками и создаёт последовательные части. Повтор команды для того же автоматического слота возвращает ту же отправку.

Telegram webhook находится по пути `/telegram/webhook/`. Он принимает только JSON с совпадающим заголовком `X-Telegram-Bot-Api-Secret-Token`, не хранит полный входящий JSON и не выполняет сетевую отправку внутри HTTP-запроса. Повторный `update_id` возвращает успех без повторного изменения настроек. Реализованы `/start`, `/settings`, `/digest`, `/stop`, `/cancel`, `/help` и кнопки полного RU/EN-onboarding. При выборе подборок callback обновляет исходное меню в одном сообщении. Черновик живёт 30 минут; старые кнопки связаны с его токеном и отклоняются.

Для первого локального теста команды пользователей можно получать через long polling без домена,
HTTPS и webhook. Этот процесс также отправляет поставленные им в очередь ответы:

```powershell
.\.venv\Scripts\python.exe manage.py run_telegram_polling
```

После настройки публичного webhook ограниченный запуск только сетевого отправителя выполняется отдельно:

```powershell
.\.venv\Scripts\python.exe manage.py send_telegram_queue --limit 100
```

Сначала отправляются ответы на команды, затем части дайджестов. `retry_after` откладывает повтор, блокировка бота помечает чат недоступным, а сетевой или серверный сбой после начала запроса переводит объект в `unknown` без автоматического повтора.

Постоянный отправитель запускается командой `run_telegram_sender`. Он держит один экземпляр через аренду и heartbeat в базе. Потерянная запись `in_flight` после десяти минут переводится в `unknown`, потому что автоматический повтор мог бы создать дубликат.

```powershell
.\.venv\Scripts\python.exe manage.py run_telegram_sender --poll-seconds 2 --batch-size 25
```

В `/settings` доступен раздел «Мои данные», также работает команда `/data`. Подтверждение удаления действует пять минут. После подтверждения подписка останавливается сразу, а идемпотентное фоновое задание удаляет рабочий профиль, настройки, доставки и связанные Telegram-квитанции. HMAC guard хранится 45 дней и позволяет следующему `/start` создать новое пустое поколение профиля. После каждого удаления он экспортируется отдельным заданием; до успешного экспорта Telegram-отправитель заблокирован.

Планировщик заранее создаёт слоты текущих разрешённых расписаний, периодический сбор активных источников и задание полного автоматического выпуска перед каждой рассылкой. Повторный проход безопасен. Для полной локальной проверки без RabbitMQ:

```powershell
.\.venv\Scripts\python.exe manage.py run_background_scheduler --once --local-execute
```

В серверном режиме отдельный процесс `scheduler` выполняет `plan_background_jobs` и `publish_outbox`, а Celery worker получает из RabbitMQ только `job_id` и версию контракта. Состояние, параметры, попытки, аренда и результат остаются в PostgreSQL. Ручные диагностические команды: `plan_background_jobs`, `publish_outbox` и `run_due_jobs`.

Слоты рассчитываются для текущей сохранённой редакции каждого разрешённого расписания. Изменение или добавление варианта не переводит на него действующих подписчиков: пользователь выбирает нужную частоту заново через `/settings`. Пользователи Django admin — сотрудники, а не подписчики Telegram.

Команда `configure_staff_roles` создаёт и синхронизирует пять групп с минимальными правами: `catalog_manager`, `editor`, `support`, `privacy_operator`, `auditor`. Ни одна группа не получает удаление объектов; владелец остаётся отдельным superuser. `configure_staff_roles --check` обнаруживает ручное расхождение прав.

Резервная копия и проверка восстановления имеют отдельный журнал в разделе «Операции»:

```powershell
.\.venv\Scripts\python.exe manage.py create_database_backup
.\.venv\Scripts\python.exe manage.py run_restore_drill backup_uuid
```

Локально команда использует согласованный SQLite backup API, сохраняет SHA-256 и проверяет копию в изоляции через `integrity_check`, таблицы и историю миграций. Это учебный контур. В production поддержан PostgreSQL custom dump: нужны `pg_dump`, `age`, `BACKUP_STORAGE_CLASS=external`, отдельный `BACKUP_OUTPUT_DIR` и публичный `BACKUP_AGE_RECIPIENT`. Проверка PostgreSQL требует отдельную пустую БД в `--target-dsn` и age identity; имя БД должно начинаться с `BACKUP_RESTORE_DATABASE_PREFIX`, а совпадение с рабочей БД отклоняется.

Плановые копии включаются только через `BACKUP_SCHEDULE_ENABLED=1`. Истёкшие артефакты очищает `purge_expired_backup_artifacts`, сохраняя строку журнала со статусом `expired`. Guard хранится в отдельном `ERASURE_GUARD_OUTPUT_DIR`, в production шифруется `age` и сохраняется не меньше 60 дней. Основная копия записывает SHA-256 связанного guard в свой manifest.

Перед первым запуском production и после восстановления выполняются:

```powershell
.\.venv\Scripts\python.exe manage.py export_erasure_guard
.\.venv\Scripts\python.exe manage.py apply_erasure_guard
```

Отправитель сверяет внешний `current.json` с состоянием восстановленной базы перед каждым сообщением. Несовпадение, отсутствие или повреждение guard останавливает ответы бота и дайджесты. `apply_erasure_guard` повторно удаляет воскресшие поколения профилей, восстанавливает актуальные tombstone и только после успешной транзакции разрешает доставку. Полная последовательность находится в [RESTORE_RUNBOOK.md](<C:/Users/Vladislavv/Documents/ChatGPT/AI-дайджесты бот/docs/RESTORE_RUNBOOK.md>). Второй фактор подключается на уровне выбранного identity/reverse-proxy перед публичным доступом.

## Linux и PostgreSQL

В `compose.yaml` подготовлено интеграционное окружение PostgreSQL, RabbitMQ и приложения. Docker на текущем компьютере не обнаружен, поэтому этот вариант ещё не запускался. Он не является готовой production-конфигурацией: теги образов нужно закрепить после проверки, настроить HTTPS, второй фактор, копии и наблюдение.

Создайте `.env` по `.env.example` и замените все примеры секретов. Для паролей в URL брокера используйте случайные URL-safe значения; файл с секретами не коммитьте. `--env-file` читает файл только для Compose; Django сам не загружает `.env`.

```sh
docker compose --env-file .env build
docker compose --env-file .env up -d db broker
docker compose --env-file .env run --rm web python manage.py migrate
docker compose --env-file .env run --rm web python manage.py import_seed
docker compose --env-file .env run --rm web python manage.py createsuperuser
docker compose --env-file .env up -d web
docker compose --env-file .env --profile workers up -d worker scheduler
docker compose --env-file .env --profile telegram up -d sender
```

База и брокер не открывают порты на хосте; веб-порт привязан к `127.0.0.1`. Профиль `workers` запускает планировщик и универсальный Celery worker. Отправитель очереди Telegram запускается отдельным процессом профиля `telegram`.
