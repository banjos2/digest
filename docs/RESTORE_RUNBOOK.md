# Восстановление базы без возврата удалённых профилей

Эта процедура обязательна для production. `DELIVERY_RECOVERY_GUARD_REQUIRED=1`, каталог
`ERASURE_GUARD_OUTPUT_DIR` и его файл `current.json` должны находиться вне тома базы и вне
каталога обычных копий.

1. Остановить sender, scheduler и worker. Не запускать Telegram-отправку во время восстановления.
2. Проверить выбранную копию командой `run_restore_drill` на отдельной БД с разрешённым префиксом имени.
3. Восстановить проверенную копию в рабочую БД штатными средствами PostgreSQL.
4. Применить миграции приложения командой `python manage.py migrate`.
5. Выполнить `python manage.py apply_erasure_guard`. Команда проверяет SHA-256 актуального
   внешнего артефакта, расшифровывает его при необходимости, удаляет поколения профилей не
   новее зафиксированного удаления и восстанавливает tombstone.
6. Проверить в админке «Операции → Безопасность доставки», что состояние равно «Разрешена» и
   хеш совпадает с последним успешным guard export.
7. Запустить web и worker, затем scheduler и sender. Sender всё равно сверяет состояние перед
   каждым сообщением и остановит обработку очереди при новом расхождении.

Если guard отсутствует, повреждён, не расшифровывается или имеет неизвестный формат, доставку
не разрешать. Ошибку исправляют восстановлением актуального внешнего артефакта; пустой guard
вместо потерянного создавать нельзя. После штатного нового развёртывания без пользователей
первичный пустой guard создаётся явной командой `export_erasure_guard`.

Тренировочный SQLite-прогон не заменяет PostgreSQL-восстановление. Production-приёмка требует
отдельную пустую БД, реальный зашифрованный артефакт и проверку этой процедуры до запуска
пользователей.
