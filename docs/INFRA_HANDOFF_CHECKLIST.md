# Данные для переноса AI-дайджестов на корпоративную инфраструктуру

Текущие Telegram-аккаунты, Telegram-бот и ключ OpenRouter сохраняются. Их секреты переносятся
в хранилище секретов инфраструктуры и не сохраняются в Git.

## Рекомендуемый контур

Для текущей нагрузки достаточно одной Linux VM с Docker Compose:

- 2–4 vCPU;
- 4–8 GB RAM;
- 40 GB SSD с возможностью расширения;
- актуальный LTS Linux;
- Docker Engine и Docker Compose v2;
- PostgreSQL 17 с расширением pgvector;
- RabbitMQ 4;
- отдельное внешнее место для зашифрованных резервных копий.

Приложение запускается отдельными постоянными процессами: web/админка, scheduler, worker,
Telegram sender и Telegram receiver. Все они автоматически перезапускаются после сбоя и старта
сервера. GPU не нужен: AI вызывается через OpenRouter.

PostgreSQL и RabbitMQ можно разместить на этой же VM для первого запуска. Управляемые сервисы
предпочтительнее, если они уже используются в организации.

## Как Telegram будет получать команды

Нужно выбрать один вариант:

1. **Polling — рекомендуется для первого корпоративного запуска.** Сервер сам подключается к
   Telegram. Публичный входящий адрес для бота не нужен, админку можно оставить только во VPN.
2. **Webhook.** Нужны публичный DNS-адрес, HTTPS-сертификат и входящий порт 443 от Telegram.

Оба варианта сохраняют полностью автоматическую работу. Для внутренней инфраструктуры polling
обычно проще и уменьшает число внешних сетевых настроек.

## Что должен предоставить инфраструктурный специалист

1. Linux-сервер или виртуальную машину и способ входа на неё по SSH через корпоративный VPN.
2. Решение, где работают PostgreSQL и RabbitMQ: на той же VM или как управляемые сервисы.
3. Внутреннее DNS-имя админки, если она должна открываться по имени.
4. TLS-сертификат и reverse proxy, если админка использует HTTPS или выбран webhook.
5. Корпоративный Git-репозиторий и право проекта публиковать контейнерный образ либо собирать его
   на сервере.
6. Хранилище секретов: Vault, Docker secrets, Kubernetes Secrets или защищённые environment-файлы.
7. Внешнее по отношению к базе хранилище резервных копий.
8. Систему логов и уведомлений либо почту/чат для аварийных сообщений.

## Сетевой доступ

С серверов приложения должен быть разрешён исходящий HTTPS к:

- Telegram Bot API;
- Telegram/MTProto для Telethon;
- `api.openrouter.ai`;
- всем сайтам и RSS-лентам из каталога источников;
- DNS и системным серверам времени.

При polling входящий доступ из Telegram не нужен. Для админки следует разрешить доступ только из
корпоративной сети или VPN. При webhook дополнительно нужен входящий HTTPS 443 из интернета.

## Секреты, которые переносятся

- `TELEGRAM_BOT_TOKEN`;
- `TELEGRAM_WEBHOOK_SECRET`, даже если сначала используется polling;
- `TELEGRAM_SOURCE_API_ID`;
- `TELEGRAM_SOURCE_API_HASH`;
- `TELEGRAM_SOURCE_PHONE`;
- файл Telethon-сессии либо новая авторизация аккаунта на сервере;
- `OPENROUTER_API_KEY`;
- `DJANGO_SECRET_KEY`;
- `ERASURE_HASH_KEY`;
- пароли PostgreSQL и RabbitMQ;
- ключи шифрования резервных копий.

Заполненные значения не передаются в чат и не коммитятся. Их вводит владелец секретов прямо в
корпоративное хранилище.

## Какие данные переносим из локальной версии

Рекомендуемый перенос:

- источники и их состояние;
- подборки и связи источников с подборками;
- варианты расписания;
- правила формирования;
- административные настройки AI-бюджета.

Не следует переносить тестовые подписки, тестовые Telegram update, очереди доставки, пробные
выпуски и журналы AI-запросов. Сотрудники заново проходят `/start` в уже рабочем боте. Такой
перенос исключает случайную отправку старой тестовой очереди.

## Что нужно решить до начала технической подготовки

Пришлите без паролей и токенов ответы:

1. Кто предоставляет сервер: ваша организация или внешний хостинг?
2. Есть ли уже Linux VM? Если да — какая ОС, CPU, RAM и диск?
3. Установлены ли Docker и Docker Compose?
4. PostgreSQL и RabbitMQ будут на этой VM или предоставлены отдельно?
5. Доступна ли VM из интернета по HTTPS, или работаем через polling и VPN?
6. Какой адрес будет у админки?
7. Куда загружать код: адрес корпоративного Git-репозитория?
8. Куда складывать резервные копии?
9. Кто из сотрудников должен входить в админку?

## Работы в проекте после получения ответов

1. Зафиксировать исходный код в Git без локальных секретов и тестовых данных.
2. Сделать production Compose-конфигурацию: `DEBUG=0`, health checks, restart policy, постоянные
   тома и ограничение публикации портов.
3. Добавить production-сервис Telegram polling либо настроить webhook.
4. Проверить PostgreSQL/pgvector и RabbitMQ на целевой Linux-системе.
5. Реализовать перенос только каталога и настроек из SQLite в PostgreSQL.
6. Добавить управляемое ограничение доступа к внутреннему боту.
7. Настроить доступ к админке, TLS и безопасные заголовки.
8. Подключить секреты и заново авторизовать Telethon либо безопасно перенести его session-файл.
9. Настроить резервные копии и выполнить пробное восстановление.
10. Провести smoke test, автоматический тестовый выпуск и суточный пилот.
11. Включить постоянные процессы и проверить автоматический перезапуск после reboot.

Текущий `compose.yaml` является интеграционным: в нём web работает с debug и привязан только к
локальному интерфейсу. Публиковать его как production-конфигурацию без перечисленных изменений
нельзя.
