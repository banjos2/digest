# Данные и контракты: основа реализации

11 сентября 2026 года. По просьбе пользователя подробное проектирование объединено с реализацией. Каталог, расписания, получение материалов, редакционные карточки, AI-бюджет и двуязычные выпуски уже представлены Django-моделями и миграциями; ниже явно отделены следующие сущности.

## Реализованные модели

| Модель | Назначение и ограничения |
|---|---|
| `OriginGroup` | Стабильный ID группы происхождения. Редакция, её каналы и переводы могут относиться к одной группе |
| `PublisherProfile` | Редакция/автор, язык, роль, происхождение, заметки и исходные сведения исследования |
| `RetentionPolicy` | Профиль хранения. Импортированный `news_default_v1` связан с источниками; команда очистки исходного текста применяет текущий срок 90 дней |
| `Collection` | Стабильный ID, RU/EN названия и описания, тип, версия продукта, активность и порядок. Видео и следующую версию нельзя активировать в v1 |
| `Source` | Уникальный URL, профиль, происхождение, язык, адаптер, RSS, профиль хранения и независимые статусы проверки. Активация требует проверенного маршрута и сборщика |
| `SourceCollection` | Уникальная пара источник–подборка, активность, пилот/резерв, назначение и фильтр. Отключение связи не удаляет источник |
| `Schedule` | Стабильный ID, RU/EN названия, daily/weekly, времена, дни, часовой пояс, подготовка и опоздание, видимость, разрешение рассылки и номер редакции |
| `ScheduleRevision` | Уникальная пара расписание–номер; снимок правила создаётся атомарно при изменении. Старую редакцию нельзя изменить через модель или админку |
| `SeedSnapshot` | Имя файла, хеш, исходный JSON и дата импорта. Уникальность имя–хеш; сохранение данных исследования без потери полей, ещё не вынесенных в модели |
| `SourceFetchState` / `IngestionRun` | Условные HTTP-заголовки, последний результат и счётчики явного запуска одного источника; тексты сетевых ошибок не сохраняются |
| `Publication` / `PublicationVersion` | Уникальный материал источника и неизменяемые версии содержимого. Повтор без изменений не продлевает срок; очистка удаляет текст, сохраняя ссылку и хеш |
| `Event` / `EventMembership` | Редакторское событие и конкретные версии публикаций с ролями основной, подтверждающей, контекстной или противоречащей |
| `EventCardRevision` | Неизменяемая RU/EN редакция для слота, до шести ссылок на материалы и хеш доказательной базы. EN указывает точную RU-редакцию; новая RU снимает старый EN с текущего состояния |
| `GroupingSuggestion` | Упорядоченная пара версий публикаций, оценка и причины сходства, версия алгоритма и решение редактора. Автоматический проход не создаёт и не объединяет события |
| `Edition` / `EditionRevision` / `EditionItem` | Подборка, редакция расписания, окно и плановый момент; неизменяемые RU/EN-версии с главными и дополнительными историями. EN связан с точной RU-редакцией и сохраняет её события, порядок и уровни |
| `AIBudgetPeriod` / `AIRequest` | Месячный лимит, резерв и расход; задача, модель, хеш входа, токены, ID ответа и стоимость без сохранения промпта и исходных текстов. Нулевой лимит блокирует вызов до обращения к провайдеру |
| `SubscriberGeneration` / `PreferenceRevision` / `SubscriptionCollection` | Поколение Telegram-профиля и шесть независимых состояний; неизменяемые версии языка, редакции расписания и выбранных подборок. Для одного пользователя допускается только одно текущее поколение и одна текущая редакция настроек |
| `Delivery` / `DeliveryManifest` / `DeliveryPart` / `DeliveryAttempt` | Идемпотентная отправка слота, зафиксированный состав выпусков и дедупликации, неизменяемые части и журнал результатов. Неопределённый результат блокирует автоматическое продолжение |
| `PreferenceDraft` / `TelegramUpdateReceipt` / `BotReply` | Ограниченный по времени черновик с токеном актуальности; уникальный Telegram update ID и хеш без хранения входного сообщения; очередь локализованных ответов и кнопок со статусом сетевой отправки |
| `ScheduleSlot` | Сохранённое окно выпуска, начало подготовки, плановое время, крайний срок и итог подготовки для конкретной редакции расписания |
| `BackgroundJob` / `OutboxEntry` | Идемпотентное задание с ограниченной схемой параметров, арендой, повторами и результатом; атомарное намерение передать в RabbitMQ только ID и версию контракта |
| `EditorialSelection` | Кандидат события для конкретных слота и подборки, пять оценок, рассчитанный балл, редакционное обоснование и решение: главное, дополнительно, исключено или отложено |
| `ProcessLease` | Единственный владелец постоянного планировщика или Telegram-отправителя, время heartbeat и срок аренды для восстановления после остановки |
| `BackupRun` | Запрос копии, тип БД и хранилища, шифрование, имя артефакта, SHA-256, размер, срок и безопасный код ошибки |
| `RestoreDrill` | Изолированная попытка восстановления конкретной копии и результаты проверок целостности, миграций и таблиц |
| `DeliverySafetyState` | Блокировка или разрешение Telegram-доставки и SHA-256 последнего применённого внешнего erasure guard |
| `ErasureRequest` / `ErasureTombstone` | Двухшаговый запрос удаления и 45-дневный HMAC guard без предпочтений; после рабочей очистки ссылка запроса на удалённый профиль обнуляется |

Стабильные ID существующих карточек в админке доступны только для чтения. Ссылочные записи защищены от удаления через `PROTECT`; опубликованные сущности будут ссылаться на конкретные редакции. Проверки активации и уникальности дополнительно существуют в базе. Изменения через прямой SQL и `QuerySet.update` не являются разрешённым способом редактирования правил приложения: они обходят историю и часть прикладной валидации.

Шесть исходных JSON читаются одной командой в общей транзакции. Сначала создаются справочники, затем источники/связи и расписания; ошибка откатывает новые записи. Повторный импорт только добавляет недостающие ID и сохраняет существующие карточки администратора. Редакционные и пользовательские политики, план пилота и полная политика хранения пока хранятся в снимках, а не объявляются подключёнными исполнителями.

## Следующие модели материалов

| Модель | Ключи и связи |
|---|---|
| `SourceArtifact` | Версия публикации, тип производного объекта, ссылка на файл/вектор, срок исходной версии. Отдельная запись метаданных переживает очистку текста только по правилам хранения |
| `Claim` / `Evidence` | Утверждение, атрибуция и статус; связь с конкретной версией, фрагментом и происхождением. Истёкший текст не изображается доступным доказательством |

Для опубликованных редакций бизнес-переходы: `draft → review → approved → published`; ошибки и сомнения ведут в `held`, доработку или исключение. Новые факты и исправления создают следующую редакцию, не меняют молча уже отправленный текст. Состояния перевода `pending / ready / stale / failed` отделены от состояния публикации.

## Реализованные подписки и подготовка доставки

`SubscriberGeneration` содержит UUID поколения регистрации, Telegram user/chat ID, языки, даты и шесть независимых измерений состояния из `config/user_flow_policy.json`. После удаления и нового `/start` создаётся новый UUID. `PreferenceRevision` хранит сохранённый выбор, а `SubscriptionCollection` — выбранные ID подборок. Административный Django User — другая сущность, он не заменяет подписчика.

`Delivery` уникальна по поколению–слоту–типу автоматической отправки. `DeliveryManifest` фиксирует редакции выбранных блоков, удаления дублей, язык и редакцию настроек до первой части. Изменение настроек отменяет неотправленное продолжение; повторной автоматической отправки того же слота не создаёт.

`DeliveryPart` уникальна по отправке–номеру и хранит хеш текста; `DeliveryAttempt` — время, результат, код ошибки и полученный `message_id`. Состояния части: `pending → in_flight → sent`; подтверждённый временный отказ ведёт в `retry_wait`, окончательный — `failed`, отмена — `cancelled`. Сбой после возможного принятия Telegram ведёт в `unknown`: автоматический повтор и продолжение набора останавливаются до явного решения. Нельзя трактовать отсутствие записи об успехе как доказательство отсутствия сообщения у пользователя.

Права проверяются перед внешним вызовом, включая `privacy_state`, доступ, паузу, язык и актуальность настроек. Уже начатый внешний вызов не отзывается отменой очереди. Минимальный индекс получатель–выпуск хранится 90 дней для исправлений; подробные попытки — 30 дней.

## Фоновые операции, бюджет и удаление

`BackgroundJob` хранит вид работы, версию контракта, ограниченные параметры, идемпотентный ключ, попытки, следующую дату, владельца/срок аренды и конечное состояние. В сообщении брокера — только `job_id` и версия контракта. Состояния: `pending → running → done`, либо `retry_wait / failed / cancelled`. Истёкшая аренда позволяет другому исполнителю забрать работу; идемпотентность прикладной операции остаётся обязательной.

`OutboxEntry` создаётся в той же транзакции, что и прикладное изменение, и передаёт ID работы в RabbitMQ. Повтор сообщения безопасен только при проверке ключа, актуальной редакции и результата в PostgreSQL. Удалённый или отменённый объект не создаётся заново исполнителем. Публикации, отзывы и секреты не копируются в payload.

Реализованный `AIRequest` связывает хеш входа, задачу, модель, версию инструкции, статус, provider request ID, токены и фактический расход. `AIBudgetPeriod` атомарно резервирует верхнюю оценку до запроса и заменяет её фактической стоимостью после ответа. Потерянный ответ регистрируется как ошибка; дальнейшая политика сверки стоимости и повторов будет уточнена по поведению выбранного API. Данные подписчика в новости для AI не передаются.

`ErasureRequest` фиксируется до подтверждения принятия пользователю. Пока удаление не завершено, `erasure_pending` запрещает новые персональные операции. После очистки в основной базе остаётся `ErasureTombstone` с HMAC-ключом на 45 дней; предпочтения, доставки и Telegram ID удаляются. Выполнение удаления атомарно блокирует доставку и ставит экспорт guard в очередь. Внешний manifest и `DeliverySafetyState` должны содержать один SHA-256; после восстановления актуальный guard повторно удаляет поколения не новее зафиксированного удаления.

Фоновые задания сбора, группировки, поиска редакционных кандидатов, генерации карточек, сборки выпуска, очистки, подготовки доставки и удаления профиля реализованы. Планировщик создаёт будущие слоты и задания повторяемо; локальный исполнитель работает без брокера, серверный путь использует transactional outbox и Celery. Постоянные процессы защищены арендой; зависшая Telegram-отправка становится `unknown`, а не повторяется автоматически.

## Проверенное и непроверенное

На текущем шаге проверены локальная база, миграции, импорт, административные формы, календарный предпросмотр, бюджетная блокировка AI, строгий ответ тестового провайдера, предложения группировки, полный RU/EN-выпуск, версии настроек подписчика и подготовка доставки. Django-проверки работают на Python 3.12 и SQLite. Конфигурация Python 3.13/PostgreSQL для CI и Docker подготовлена, но не запускалась. Ни одной платной AI-операции, проверки реального источника или отправки в Telegram не выполнялось.
